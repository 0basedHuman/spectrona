Part 1

The strategic problem

D001 committed to one thing: ship a local scanner, because it is the fastest path to adoption. Sixty-four sessions later the scanner is 2,285 lines and has never been published to PyPI, npm, or a Homebrew tap. The other 13,000 lines are a man-in-the-middle proxy for all AI traffic, a memory subsystem with replay and compaction, LaunchAgent plists, VS Code routing, and local-LLM fallback — every one of them built for zero users.

The mechanism that caused this is visible in the session log. Each session ends with a passing check count, and that count only ever grows: 91, 96, 101, 107, 112. Adding code raises the number. Shipping does not. The validation gate, which was meant to enforce rigor, has become a treadmill that reliably feels like progress while adoption stays at zero.

A security tool nobody has installed has the same real-world impact as no security tool. The scanner is the product; everything else is deferred until it has users.

This matters more than any single bug below, because it explains them. Detection quality is the entire value of a scanner, and detection quality received a fraction of the engineering that went into the dashboard.

Part 2

Defects, in severity order

Every finding here was reproduced against the code in this repo. The terminal blocks are real output, not illustrations.

CriticalF1 · detection

The scanner's flagship rule inspects the wrong field

mcp-inspector/src/mcp_inspector/detectors/secrets_detector.py

SECRET_KNOWN_PREFIX is the only CRITICAL rule in the product, and it reads config.get("env") and nothing else. Secrets passed as command-line arguments are invisible to it.

# two live-format credentials in args
{"mcpServers":{"svc":{"command":"npx","args":[
   "-y","some-server",
   "--api-key","sk-proj-REALSECRETVALUE123456",
   "--token","ghp_ABCDEFGHIJKLMNOP1234"]}}}

$ mcp_inspector scan mcp --file args_secret.json --json
  findings: ['MCP_UNPINNED_PACKAGE', 'MCP_NO_AUDIT_LOG']
  SECRET_KNOWN_PREFIX detected? False
  summary: {'critical': 0, 'high': 0, 'medium': 1, 'low': 1}

The rule's own why_it_matters text cites credentials being "visible in process lists." Arguments are exactly what ps aux exposes; environment blocks are the harder-to-read half. The rule states the right threat and then checks the wrong surface.

FixWalk the entire server object — args, env, command, and any nested keys — through one shared detector, rather than reading a single field.
CriticalF2 · runtime

The MCP proxy blocks ordinary English

runtime-guard/src/runtime_guard/mcp_proxy.py · _contains_shell_token

Shell risk is decided by substring search for shell, exec, terminal, bash, and run_command across every string in the arguments, at any depth. The shipped default policy denies on shell risk. Together these block normal work.

shell_risk=True  write_file('In a nutshell, the executive team approved it.')
shell_risk=True  create_note('...the exec summary for the terminal illness study')
shell_risk=True  write_file('We shall execute the plan.')
shell_risk=True  write_file('Seashells by the seashore')
shell_risk=True  save({'command': 'anything at all'})   # key name alone

# end to end, default policy, benign note:
{"error":{"code":-32041,
  "message":"Spectrona policy blocked this MCP tool call.",
  "data":{"policy_rule_id":"deny-shell-risk","shell_risk":true}}}

Six of six benign strings blocked. A user who wires this in front of their MCP servers loses the ability to write a document containing the word "executive."

Compounding it, require_approval has no approval path — PHASES.md still lists "Approval prompt UX" as unchecked — so it resolves to a hard JSON-RPC error with no way for a user to proceed.

FixMatch on structure, not prose: the tool's declared schema and the argument keys that actually reach a shell, never free-text content. Until the false-positive rate is measured on real traffic, ship dry-run as the only mode.
CriticalF3 · gateway security

Mutating endpoints have no authentication

spectrona-gateway/src/spectrona_gateway/app.py

create_app() registers ten routers and installs no middleware, no dependency, and no token check. The endpoints that rewrite the user's Claude, Codex, and VS Code configuration and replace the active security policy are reachable by any local process, and by any web page the user visits.

# any page in the user's browser can execute this.
# Content-Type: text/plain is a CORS "simple request" — no
# preflight. CORS hides the *response*, not the side effect.

fetch('http://127.0.0.1:8787/policy/presets/relaxed/apply', {
  method:'POST', mode:'no-cors',
  headers:{'Content-Type':'text/plain'},
  body:'{"confirm":true}'
})
// -> the user's security policy is now "relaxed"

The confirm: true body field is a guard against accidents, not against an attacker; it is trivially supplied. Binding to localhost is not an authentication boundary — this is the standard DNS-rebinding and CSRF surface that local agents get exploited through. In a security product, it is disqualifying.

FixGenerate a bearer token into ~/.spectrona/config.yaml at init and require it on every non-health route; validate Origin and Host to close rebinding; never bind 0.0.0.0.
HighF4 · protocol

The proxy desynchronizes on spec-legal notifications

runtime-guard/src/runtime_guard/mcp_proxy.py · _forward_to_upstream

The forwarder writes one line and reads exactly one line back, assuming strict request/response alternation. MCP is bidirectional: servers legitimately emit log and progress notifications, and may initiate sampling requests. The first notification is consumed as if it were the reply.

Client asked: tools/list  (id=7)
Client GOT  : {"jsonrpc":"2.0","method":"notifications/message",
               "params":{"level":"info","data":"listing tools"}}

-> a notification, not the result. No id. Tool list lost.
-> the real reply stays buffered, shifting every later call by one.

Nothing pumps the upstream's stdout except this one synchronous read, so server-initiated messages have no route to the client at all. stderr is sent to DEVNULL, so when the wrapped server crashes the user sees silence.

FixTwo pumps and a pending-request map keyed by JSON-RPC id: correlate replies, pass notifications through in both directions, surface upstream stderr to the Spectrona log.
HighF5 · detection

The DLP engine misses most real credential formats

spectrona-gateway/src/spectrona_gateway/dlp.py — 40 lines, 10 prefixes

This module is the sole protection between the user's traffic and their provider, and it is one regex over a ten-entry prefix list.

ok    Anthropic          sk-ant-api03-...
MISS  Stripe live        sk_live_51H8xYz...     # underscore, not dash
MISS  Google API         AIzaSyD-1234...
MISS  SendGrid           SG.AbCdEfGh1234...
MISS  HuggingFace        hf_AbCdEfGhIjKl...
MISS  Slack webhook      hooks.slack.com/services/T00/B00/...
MISS  RSA private key    -----BEGIN RSA PRIVATE KEY-----
MISS  Postgres URL       postgres://admin:SuperSecret123@db...
MISS  JWT                eyJhbGciOiJIUzI1NiJ9...
MISS  AWS secret key     wJalrXUtnFEMI/K7MDENG/bPxRfiCY...
MISS  GitLab PAT         glpat-AbCdEfGhIjKl...

  -> 10 / 12 real formats undetected

The repo scanner's entropy rule is a partial backstop, but on a three-line .env it caught only the Stripe key and missed both the Postgres password and the AWS secret. Separately, dlp.py and secrets_detector.py maintain duplicate prefix lists that must be hand-synchronized and have already diverged in behavior.

FixOne shared detection library used by scanner, gateway, and proxy. Layer it: prefix match, then entropy, then structural validation — Stripe, AWS, and GitHub tokens all carry verifiable checksums, which is how you buy precision instead of trading it away.
HighF6 · policy engine

Policy parsing fails open, and an empty rule matches everything

policy-engine/src/policy_engine/{loader,engine}.py

Policy is read by a bespoke ~90-line YAML subset parser. Two failure modes follow directly from it, and both are silent.

A. a rule with no match block matches every request
   rules:
     - id: typo-rule
       action: deny          # match: block omitted
   benign request -> deny (rule=typo-rule)

B. a misspelled match key silently disables the rule
   match:
     shel_risk: true         # typo
   shell_risk=True -> allow (rule=default)   # should deny

Case A is a denial of service against the user's own toolchain from a single omitted line; case B silently removes a control the user believes is protecting them. _match_value returns False for any key it does not recognize, so every future typo inherits case B.

FixValidate against a schema at load and refuse to start on an unknown key or an empty match. Treat a policy parse error as fatal, never as a permissive default. Depend on a real YAML parser — this is the one file where a bespoke parser is indefensible.
MediumF7 · signal quality

Unactionable rules manufacture noise on correct configurations

Scanning a setup built straight from Anthropic's own MCP documentation — environment variables referenced properly, filesystem scoped to the repo — produces six findings.

[MEDIUM] MCP_UNPINNED_PACKAGE  @modelcontextprotocol/server-filesystem
[MEDIUM] MCP_UNPINNED_PACKAGE  @modelcontextprotocol/server-github
[MEDIUM] MCP_UNPINNED_PACKAGE  mcp-server-sentry, ${SENTRY_TOKEN}
[LOW   ] MCP_NO_AUDIT_LOG      x3, one per server

summary: {critical: 0, high: 0, medium: 3, low: 3, total: 6}

${SENTRY_TOKEN} is an environment reference being reported as an unpinned package. More seriously, MCP_NO_AUDIT_LOG fires on every server that will ever be scanned: auditLog is not a field in the MCP specification. The safe fixture had that key added to it so validation would pass, which means the rule's clean case was manufactured rather than found.

For a scanner this is not cosmetic. A user's first run is their only run; six noise findings teach them the tool is unreliable, and that is precisely the mechanism by which a scanner ends up unused.

FixDelete MCP_NO_AUDIT_LOG — an unactionable finding is worse than none. Skip ${…} references in the package rule. Hold every rule to a published precision target before it ships.
MediumF8 · architecture

D002 is documented but not implemented

The decision log states rules live in YAML rather than code so that the community can contribute without touching the scanner. No code path loads those YAML files. Grepping the entire scanner source for a rules-file read returns nothing; the only matches are docstrings that describe the YAML. Detection is hardcoded Python, and the four rule files are documentation that resembles configuration.

This is worth correcting because the community-contributed rule set is the most plausible long-term moat in the plan, and right now the barrier to contributing a rule is a Python pull request against a codebase with no unit tests.

FixEither make the loader real — declarative matchers over parsed config, with the Python detectors reduced to primitives the YAML composes — or amend D002 to say detection is code. Do not leave the log describing a system that does not exist.
MediumF9 · testing

There are no unit tests, and the check count is not measuring quality

No test_*.py, no conftest.py, no pytest configuration anywhere in the repo. The 174 Phase 1 "checks" are bash assertions that grep for strings in CLI stdout.

That harness verifies a finding's ID appears in output. It cannot express the things that decide whether this product is trustworthy: the false-positive rate across a corpus of real configurations, that redaction never emits a substring of a known secret, that the policy loader rejects malformed input. Every defect above sits in exactly that blind spot — F1 through F7 all pass the current suite.

The count also creates the wrong incentive. "112/112" reads as rigor while measuring volume, and the number rises fastest when you add rules, including rules like F7's that should not exist.

Fixpytest per detector with a fixture corpus; property tests for redaction; golden files for reports. Keep bash for end-to-end smoke only. Replace the headline metric with precision and recall against the corpus.
Part 3

What would make it exceptional

The opportunity is real. MCP is spreading quickly, the risk is genuine, and no tool owns this category yet. The path to owning it is narrower than the current roadmap and needs less code than already exists.

  1. Build the corpus, and make precision the headline number

    the moat

    Harvest a thousand real mcpServers configurations from public GitHub, run the scanner over them, and hand-label the results. This single asset does three jobs at once: it makes the false positives in F1 and F7 measurable instead of arguable, it becomes the regression suite F9 is missing, and it is the launch story — "we scanned 1,000 public MCP configs and 34% leak credentials" is a post that gets read, and the tool that produced it gets installed. Anyone can write regexes; nobody else has the benchmark. Gate every rule on ≥95% precision before it ships.

  2. Rebuild detection as one verifier-based library

    correctness

    Collapse dlp.py and secrets_detector.py into a single package consumed by scanner, gateway, and proxy, so a format is added once. Layer the checks the way gitleaks and TruffleHog do — prefix, then entropy, then structural validation against each provider's known token format. Scan args, env, command, and nested values. Keep live verification off by default; D004 is the right call and is a genuine differentiator worth protecting.

  3. Ship where the users already are

    distribution

    A scanner run once by hand is a scanner run once. Three integrations change that, and all three are days of work rather than months. SARIF output is the highest leverage item in this document: it lands findings in the GitHub code-scanning tab and the VS Code SARIF viewer for free. A GitHub Action puts the scan on every pull request, which is where security scanners actually live. And npx — the MCP audience is a Node audience, and npx spectrona will out-install a Homebrew formula that needs a tap, a Python runtime, and a PYTHONPATH shim.

  4. Turn the runtime layer into observability, not enforcement

    reframe

    No one will place a beta proxy in the blocking path of their tools, and given F2 they would be right not to. But "here is every tool call your agent made, every file it touched, everything it sent outbound" is valuable on day one, safe to adopt, and honest about what the product currently knows. Ship dry-run as the only mode; earn blocking after the corpus proves the false-positive rate. This inverts a deny-by-default design built on an inaccurate detector into something people can actually install — and it reuses most of the code already written.

  5. Build approval, or remove the action

    honesty

    An approval action with no way to approve is a defect wearing a feature's name. The small honest version: block, notify, expose a pending queue, let spectrona approve allowlist that specific tool-and-argument shape for the session. Until that exists, alias require_approval to deny with a message that says so.

  6. Delete what has no user

    focus

    Memory replay, compaction, timeline, staleness, context packages, and session extraction total roughly 1,500 lines of Phase 3 written while Phase 1 was still unshipped. Local-LLM fallback routing, VS Code terminal routing, and LaunchAgent plists are in the same category. Branch them and remove them from the trunk. Each line is maintenance and review surface on a product with no adoption, and the review burden is a large part of why detection quality never got the attention it needed.

The one-sentence version

The engineering discipline in this repo is real — the audit trail, the redaction habits, the local-first commitment are all better than most projects at this stage — but it has been pointed at breadth instead of at detection quality, and detection quality is the only thing a security scanner is. Spend the next month making the scanner accurate, benchmark it in public, put it in CI, and delete the rest until someone asks for it.
